# CarbonSlice

**An AI-powered carbon accounting product, built solo, 0→1.**

Small businesses upload their utility bills and fuel receipts. An LLM extracts the structured data. Anything the model isn't confident about routes to human review. The output is a Scope 1 + 2 carbon footprint where every figure traces back to the exact text on the source document.

This repository is both the product and the build log. I'm an ESG/PropTech product manager with a decade in carbon accounting and utility data at enterprise scale, building this to work hands-on with the AI-native layer — LLM extraction, evals, human-in-the-loop design, and production AI risk. The domain depth is why this project works as a learning vehicle: I can judge the model's output myself, so I am the eval ground truth.

---

## The core loop

```
bills & receipts  →  LLM extraction  →  confidence triage  →  human review  →  Scope 1+2 footprint
                     (multimodal)       (per field)           (confirm/correct)   (full lineage)
```

**Design commitments**, held from the start:

- **Emission factors are never generated by the model.** They come from a versioned DEFRA factor table, and every reported tonne records which factor version produced it.
- **Full audit lineage.** Every extracted value carries the source text it came from; every human action records what the model originally said.
- **Null over invention.** A confident null on an absent field is correct behaviour. A plausible fabrication is a failure, and is scored as its own error class in evals.
- **Confidence thresholds are a product lever, not a constant.** The threshold sets the review rate, and the review rate *is* the cost model.

## Findings so far

Three things I learned by building rather than reading:

**Dual-fuel bills broke the schema, not the extraction.** A flat schema with one `consumption_value` structurally cannot represent a bill carrying two fuels. The fix was a data-model redesign — a bill is document metadata plus a `supplies[]` array, one entry per fuel. Real documents force schema decisions that whiteboards don't.

**Schema growth has a token price, paid on every extraction.** Adding fields in v2 reconsumed the output budget and reintroduced a truncation failure I'd already fixed once. The answer was a compact wire format, budgeted verbosity, and graceful degradation: when space runs short the system sheds source text on cosmetic fields, never on values, and never on lineage for emissions-bearing fields — and it flags that it degraded, because degrading silently is worse than failing.

**Schema versions invalidate accuracy history.** Results scored against v1 aren't comparable to v2. Every eval run now records the schema version it scored against. Discovered here at zero cost; in production this is the difference between a trustworthy accuracy dashboard and a misleading one.
